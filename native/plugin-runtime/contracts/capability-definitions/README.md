# Trusted capability definitions

This contract makes the permission vocabulary extensible without letting plugins define their own authority. Omarchy packages and local administrators install definitions; a plugin manifest can only reference an exact canonical name, definition generation, and definition digest. Unknown, stale, or replaced definitions fail closed.

A definition binds one canonical authority identity to its scope schema, operations, trusted UI title and risk text, gesture requirements, revocation behavior, audit redaction policy, adapter class, adapter ABI, and semantic contract digest. The contract digest identifies the bounded provider protocol and its semantics; executable identity belongs to the separately trusted provider profile. Publisher rationale remains untrusted manifest prose and is not part of this trusted definition. Two names cannot point at the same authority identity or identical adapter/operation binding, preventing a dangerous adapter from being relabeled as a harmless permission.

The closed enforcement families describe durable authority rather than products: bounded network fetch, gesture-bound external URI opening, sanitized system observation, selected-device observation/control, selected remote-account read/write, activation-bound media playback, and exact CLI harness execution. Each family has one exact scope schema; a remote account cannot be presented as an HTTPS origin, a device cannot be presented as an arbitrary adapter resource, and media can use only activation-bound source handles and controls. A trusted definition can choose a namespaced canonical ID, trusted display category ID and label, UI wording, operation names, and adapter instance without rebuilding Omarchy. A new scope grammar or enforcement family still requires code review. Product- or service-specific implementations belong in independently packaged provider profiles, not hard-coded permission enums. Opaque resource handles and trusted labels connect a grant to a concrete installed provider without giving the plugin a provider-selection escape hatch.

## Definition documents and trust roots

`canonical_definition_document` emits the bounded `omarchy-capability-v1` line format. It is strictly ordered, contains no escaping or duplicate-field ambiguity, caps documents at 16 KiB and operations at 16, and binds generation, definition digest, adapter class, adapter ABI, and semantic `contract-digest`. The build-only catalog generator owns the eight generic package definitions and emits both their `.capability` documents and a read-only reference index from one source of truth. It is not installed. The index helps manifest tooling obtain exact generation and definition-digest pins; it does not let a manifest omit or dynamically select them. The installed loader accepts a pre-opened package or local-admin trust root only when the directory is owned by the expected trusted UID with mode `0755` and every `.capability` file is owned by that UID, single-link, regular, mode `0644`, and opened with `O_NOFOLLOW`. Symlinks, hard links, special files, unknown filenames, unstable metadata, oversized documents, digest changes, duplicate definitions, and alias-equivalent adapter/operation bindings reject the entire directory transaction.

Provider availability is evaluated separately at consent presentation and runtime composition, so a trusted definition remains reviewable while its exact adapter service is absent.

The trusted host loads package-owned `/usr/lib/omarchy/plugin-security/<runtime-version>/capabilities.d` first and then, when present, administrator-owned `/etc/omarchy/plugin-capabilities.d`. Both roots are pre-opened by the trusted native bootstrap and passed as descriptors; QML, plugin data, and environment strings never select them. Directories must be root-owned mode `0755`; every definition must be a root-owned, single-link, regular mode-`0644` file; directory enumeration and file reads must remain metadata-stable for the complete load. One invalid administrator definition fails the complete host composition. Package definitions therefore cannot be shadowed by a local definition, and plugin revision and private-state mounts are never searched or accepted as definition roots. The loader takes the expected UID explicitly so disposable tests do not silently infer trust from the process UID.

The administrator root extends definitions for provider contracts recognized by the trusted host. It is not a native-module loading directory. An independently packaged provider still needs a bounded authenticated IPC protocol, service identity, executable/content pinning, confinement, update lifecycle, and trusted provider profile before its definition can become available. Until that provider protocol exists, dropping an executable or shared library beside a definition grants nothing and causes no code to load. A missing provider cannot be granted during review. Required granted permissions prevent activation while unavailable; optional granted permissions run degraded with an empty effective operation mask without changing durable consent. An explicitly denied permission never becomes granted merely because a provider appears.

Registry insertion rejects canonical-name and authority-identity collisions and rejects relabeling an identical adapter/operation binding. Provider enrollment, replacement administration, and privileged definition installation are not implemented; this contract exposes no installation shortcut and does not mutate `/etc`.

## Request-to-broker bridge

Schema-v2 capability request objects may carry `definitionGeneration`, `definitionDigest`, and `operations` alongside their ordinary canonical scope members. Those three reference fields are all-or-none, bounded, canonicalized into the source-request fingerprint, and exposed by the manifest model. `dynamic_request_from_manifest` accepts them only when the exact installed definition resolves.

`DynamicRequest` is the post-manifest form: an exact definition reference, requested operation subset, canonical scope, and requiredness. `DynamicGrant` repeats that exact reference, narrows operations and scope, records state, and carries a nonzero epoch. A trusted scope validator owns subset semantics for its frozen `ScopeSchema`; unknown, invalid, incomparable, or expanded scope fails closed.

`DynamicRevisionGrant` binds that request and grant to the plugin revision, policy fingerprint, and generation. Its bounded deterministic encoding is the persistence record used for review and activation; decoding never implies approval, and `review_dynamic_grant` re-resolves the current definition and revalidates exact identity, operation narrowing, epoch, and scope narrowing. The dynamic invoke envelope carries the exact definition reference, operation token, canonical demand scope, and at most 32 KiB of schema-bounded provider payload.

`dispatch_dynamic_invocation` is the broker gate for that envelope. It requires the authenticated channel's complete activation binding to equal the persisted revision, the invocation reference to equal the manifest request, authorization through the reviewed dynamic grant, and the live adapter's class, ABI, and semantic contract digest to equal the trusted definition. Only then does it invoke the injected adapter callback. The end-to-end adversarial test covers spoofed definition name/digest/generation and adapter contract, undeclared operations, narrowed and expanded scopes, denied and revoked grants, stale plugin revision/generation, unknown definitions, malformed persistence, and bounded response dispatch.

Compiled capabilities remain the bootstrap path in `BrokerCore`; dynamic definitions use their own bounded message envelope and do not extend `OperationId`. Consent review reconstructs exact `DynamicRevisionGrant` values, `AuthorityStore` persists them with the activation snapshot, and `SessionRuntimeFactory` installs the resulting routes in `DynamicBrokerRuntime`. `StructuredBroker` selects the dynamic route only for a reviewed definition reference and never falls back to a similarly named compiled capability.

CLI profiles identify one absolute non-shell executable by digest, exact working directory, fixed environment entries, closed subcommands, positional argument grammar, byte limits, and timeout. Authorization returns an argv vector for direct execution; it never produces a command string and rejects `bash`, `sh`, `env`, unknown subcommands, extra arguments, malformed bounded values, and executable replacement. Actual process launch remains an injected trusted callback downstream.
