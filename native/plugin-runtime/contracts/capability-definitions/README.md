# Trusted capability definitions

This contract makes the permission vocabulary extensible without letting plugins define their own authority. Omarchy packages and local administrators install definitions; a plugin manifest can only reference an exact canonical name, definition generation, and definition digest. Unknown, stale, or replaced definitions fail closed.

A definition binds one canonical authority identity to its scope schema, operations, trusted UI title and risk text, gesture requirements, revocation behavior, audit redaction policy, adapter class, adapter ABI, and implementation digest. Publisher rationale remains untrusted manifest prose and is not part of this trusted definition. Two names cannot point at the same authority identity or identical adapter/operation binding, preventing a dangerous adapter from being relabeled as a harmless permission.

The closed enforcement families describe durable authority rather than products: bounded network fetch, gesture-bound external URI opening, sanitized system observation, opaque device observation/control, constrained media streaming, and exact CLI harness execution. A trusted definition can choose a namespaced canonical ID, trusted display category ID and label, UI wording, operation names, and adapter instance without rebuilding Omarchy. A new scope grammar or enforcement family still requires code review. GitHub, AirPods, Radio Browser, and compositor implementations are adapter registrations, not hard-coded permission enums. Opaque resource handles and trusted labels connect a grant to a concrete installed adapter without giving the plugin an adapter-selection escape hatch.

## Definition documents and trust roots

`canonical_definition_document` emits the bounded `omarchy-capability-v1` line format. It is strictly ordered, contains no escaping or duplicate-field ambiguity, caps documents at 16 KiB and operations at 16, and binds generation, definition digest, adapter class, adapter ABI, and adapter implementation digest. The loader accepts a caller-selected package or local-admin trust root only when the directory and every `.capability` file are regular, owned by the expected trusted UID, not group/other writable, and opened with `O_NOFOLLOW`. Symlinks, special files, unknown filenames, oversized documents, unavailable adapters, digest changes, duplicate definitions, and alias-equivalent adapter/operation bindings reject the entire directory transaction.

The intended roots are package-owned `/usr/lib/omarchy/plugin-capabilities.d` and administrator-owned `/etc/omarchy/plugin-capabilities.d`; plugin revision and private-state mounts must never be accepted as definition roots. The loader takes the expected UID explicitly so disposable tests and future system/user deployment policy do not silently infer trust from the process UID.

## Request-to-broker bridge

`DynamicRequest` is the post-manifest form: an exact definition reference plus the requested operation subset. `DynamicGrant` repeats that exact reference, narrows the operation set, records state, and carries a nonzero epoch. `authorize_dynamic_operation` resolves the installed definition and then checks definition generation/digest, manifest declaration, registered operation, grant state and operation scope, running adapter class/ABI/digest, and gesture policy. Its returned authorization contains only trusted definition and operation pointers plus the grant epoch for a broker dispatch record.

Today this bridge is standalone and directly tested; the schema-v2 JSON parser and broker wire still use their compiled bootstrap registry. The next integration step is mechanical but security-sensitive: translate manifest capability objects into `DynamicRequest`, persist `CapabilityReference` in the grant store, allocate broker operation handles from the resolved definition, and require `DynamicAuthorization` before adapter dispatch. Until that lands, dynamic documents are not activation authority and must not be advertised as enabled.

CLI profiles identify one absolute non-shell executable by digest, exact working directory, fixed environment entries, closed subcommands, positional argument grammar, byte limits, and timeout. Authorization returns an argv vector for direct execution; it never produces a command string and rejects `bash`, `sh`, `env`, unknown subcommands, extra arguments, malformed bounded values, and executable replacement. Actual process launch remains an injected trusted callback downstream.
